## 1. Архитектура трёхслойного хранилища (`raw → clean → mart`)

В рамках работы реализован воспроизводимый пайплайн пересборки трёхслойного хранилища в каталоге `Lab6` на базе двух источников данных Варианта 2 («Книги и авторы»): HTML-каталога `books.toscrape.com` и REST API `Open Library`:

* **`raw/`** — неизменяемый сырой слой в формате JSON Lines (`books_toscrape.jsonl`, `openlibrary_api.jsonl`), содержащий **396** записей (**204** из `openlibrary_api` и **192** из `books_toscrape_html`), включая синтетически загрязнённые/проблемные строки и дубликаты.
* **`clean/`** — очищенный слой данных после шестишаговой нормализации, дедупликации и проверки по контракту **Pydantic v2**: **370** валидных книг и **60** авторов (**15** записей отправлено в карантин/отбраковку, доля валидных записей от сырых — **93.43%**, доля отбраковки — **3.79%**).
* **`db/warehouse.db`** — реляционное хранилище в **SQLite** (инициализируется по схеме `db/schema.sql`), поддерживающее идемпотентную загрузку (`UPSERT`), историю наблюдений (`book_history`) и целостность данных на уровне СУБД (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`).
* **`mart/`** — аналитический слой в формате **Parquet** (`snappy`), включающий агрегированные витрины (`category_summary.parquet`, `author_stats.parquet`, `price_rating_bands.parquet`) и партиционированные снапшоты (`mart/snapshots/dt=2026-11-18/`, **370** записей в первой партиции).

## 4. Сравнение форматов хранения (CSV, JSON Lines, Parquet)

Бенчмарк выполнен на выборке из **37 000** строк (`clean/format_benchmark.csv`):

| Формат | Строк | Размер, КБ | Чтение всех столбцов, мс | Чтение 2 столбцов, мс | Тип `collected_at` | Пример `catalog_code` |
| :--- | :---: | :---: | :---: | :---: | :--- | :---: |
| CSV | 37000 | 3255.73 | 43.26 | 25.07 | `object` | `1000` |
| JSON Lines | 37000 | 6651.76 | 239.60 | 245.61 | `datetime64[ns, UTC]` | `1000` |
| Parquet (`snappy`) | 37000 | 50.56 | 391.94 | 13.45 | `datetime64[ns, UTC]` | `01000` |

**Выводы по форматам:**
* **Сжатие:** `Parquet (snappy)` занимает всего **50.56 КБ** — это в **64.4 раза** меньше CSV (**3255.73 КБ**) и в **131.6 раза** меньше JSON Lines (**6651.76 КБ**).
* **Проекция столбцов:** при чтении только 2 столбцов Parquet отрабатывает за **13.45 мс** (в **1.86 раза** быстрее CSV и в **18.26 раза** быстрее JSON Lines).
* **Типизация и схемы:** Parquet и JSON Lines сохраняют тип `datetime64[ns, UTC]` и ведущие нули в строковых кодах (`01000`), тогда как CSV парсит даты как `object` и теряет ведущий ноль (`1000`) при числовой интерпретации. При чтении всех столбцов целиком CSV остаётся быстрым за счёт простого последовательного парсинга, но уступает Parquet в аналитических запросах по подмножеству колонок и объёму хранения.

## 5. Идемпотентная загрузка в SQLite, история и ограничения БД

Загрузка в `db/warehouse.db` проверена в 3 последовательных прогонах (`run_idempotency_demo`):

| Сценарий | Передано книг | Всего книг в БД | Обновлено книг | Всего авторов в БД | Обновлено авторов |
| :--- | :---: | :---: | :---: | :---: | :---: |
| Прогон 1: первичная загрузка | 370 | 370 | 370 | 60 | 60 |
| Прогон 2: повтор с теми же данными | 370 | 370 | 0 | 60 | 0 |
| Прогон 3: изменены 2 записи | 370 | 370 | 2 | 60 | 0 |

Повторный прогон с идентичными данными не создаёт дублей и не перезаписывает неизменённые строки (`обновлено_книг = 0`, `обновлено_авторов = 0`), а изменение 2 записей обновляет ровно эти 2 записи в основной таблице и фиксирует динамику в таблице истории `book_history` (например, изменение `stock` с `20` на `24` для `upc:6957f44c3847a760` и `price` с `53.74` на `58.74` для `upc:90fa61229261140a`).

Проверка ограничений целостности на уровне SQLite (`run_constraint_tests`):

| Проверка ограничения БД | Результат | Сообщение СУБД |
| :--- | :---: | :--- |
| 1. Отрицательная цена (`CHECK price > 0`) | отклонено СУБД | `CHECK constraint failed: price IS NULL OR CAST(price AS REAL) > 0` |
| 2. Рейтинг вне диапазона `1..5` (`CHECK rating BETWEEN 1 AND 5`) | отклонено СУБД | `CHECK constraint failed: rating IS NULL OR rating BETWEEN 1 AND 5` |
| 3. Дублирующийся первичный ключ (`PRIMARY KEY book_key`) | отклонено СУБД | `UNIQUE constraint failed: books.book_key` |
| 4. Несуществующий автор (`FOREIGN KEY author_key`) | отклонено СУБД | `FOREIGN KEY constraint failed` |

## 7. Сопоставление «код vs no-code (n8n)» и правовые аспекты

### 7.1. Реализация в n8n и сравнение с кодом

Для проверки no-code подхода собран workflow в **n8n** на подмножестве из **40** записей (`Schedule Trigger` → `Code: Normalize 4 Fields & Business Key` → `Remove Duplicates (by book_key)` → `IF: Validate Record` → ветки `Convert to File (Valid CSV)` и `Convert to File (Rejects CSV)`).

* **Фактический результат запуска в n8n:** вход **40 items** → после дедупликации по `book_key` **39 items** (удалён 1 дубликат) → после `IF: Validate Record` **34 items** в ветке `true` (`nocode_result.csv`, 35 строк с заголовком) и **5 items** в ветке `false` (отбраковка: пустой `title`, отсутствующий `book_key`/URL, нечисловая цена, отрицательная цена `-14.5`, некорректный URL без схемы).

| Критерий | Реализация в коде (Python + SQLite + Parquet) | No-code реализация (n8n) |
| :--- | :--- | :--- |
| Объём и воспроизводимость | Полный набор (**396** сырых записей → **370** книг, **60** авторов), детерминированный запуск CLI и Jupyter | Тестовое подмножество (**40** записей), визуальный граф в редакторе n8n |
| Очистка и дедупликация | 6 документированных шагов с протоколом изменений и сохранением самой свежей записи | Нормализация полей и ключа в узле `Code`, дедупликация по `book_key` узлом `Remove Duplicates` (`40 → 39`) |
| Валидация контракта | Строгие схемы Pydantic v2 (диапазоны, типы, UTC, согласованность полей) + 15 записей в `rejects` | Базовая условная фильтрация в узле `IF` (`34` валидных / `5` отбракованных) |
| Загрузка и СУБД | Идемпотентный `UPSERT` в SQLite (`warehouse.db`), таблица `book_history`, `CHECK`/`UNIQUE`/`FK` | Выгрузка в CSV (`Convert to File`); прямой `UPSERT` в локальный SQLite без серверной БД (Postgres/MySQL) в стандартном узле недоступен |
| Контроль качества и витрины | 8 метрик «светофора», gate-проверка, витрины и снапшоты в Parquet (`snappy`) | Ручной просмотр счётчиков и CSV-файлов; метрики «светофора» и снапшоты в Parquet не формируются |
